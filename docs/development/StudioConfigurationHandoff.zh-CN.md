## 3. Core 配置契约：实现必须满足的规则

### 3.1 输入、解析完成和运行资源分层

1. 原始输入保存“有无提供”、原 token 和位置。缺失独立于合法的 0、false、none 和空路径。
2. 条件检查在已有选择上执行：不知道 EOS 时不猜 IdealGas，也不猜其下游必填字段。
   对当前已知条件一次返回全部可判断问题，并标明尚未解析的依赖。
3. 用受控构造生成完整、只读的运行配置。直接 C++ 调用、CLI、inspection、Setup
   使用同一类型／条件判定；不是只在 GUI 或参数追踪模式中严格。
4. Setup 前提供完整的实际需求；需求沿 ProblemGenerator 声明，不能执行任意不完整 Setup
   来试探第一个异常。Setup 的登记模型值／派生值有来源；修改后重新完成检查。
5. 配置失败不创建 Driver、模拟输出或 CUDA 资源；错误统一捕获。静态 inspection
   仍不执行 Setup、不加载 EOS、不初始化 CUDA、不检查路径是否存在。
6. 科学运行与设备视图保留普通数值，不把 optional、字符串或缺项检查带入单元循环。
   用户继续只需两个公开头文件，`Setup` 存成员、`Init` 用成员的契约保持。

当前 95 项分类为 19 常规必需、50 条件必需、25 允许登记默认和 1 个 G 退役项；
逐项条件以配置完整性计划为准。数量用于审计，GUI 按当前 binary 的目录生成界面，
不能硬编码总数或把 95 次完整模拟作为缺项矩阵。

对 case 参数建立同一来源和需求声明。登记的模型定义可合法提供必需值；
`Get(key, default)` 中一个数字本身不能自动变成已批准的物理默认。
先完成所选 case／组分的声明再判断未知键；已声明但本次未消费的条件参数不能误报拼写错误。
动态分支尚未检查时明确覆盖边界，不能以“标准参数完整”冒充全部用户 C++ 已验证。

### 3.2 错误、保留策略与退役

- 未知方法、坏数值、非法整数／布尔、无等号非注释行、空键、重复键明确失败。
  重复键给出两个位置；缺项给出键和条件，不伪造行号。拼写建议不能自动改输入。
- `compute_backend=auto`、`use_nse=auto`、合法别名、算法拒步／降阶按现有规则保留。
  `compute_backend=cuda` 不可用时明确失败；不能静默改为 CPU 来完成 GPU 验收。
- 关闭模块不要求它的专属输入；开关本身缺失不等于关闭。不适用的合法显式值保留；
  格式错误仍报错。EOS 禁止显式出现的扩散常量键仍须明确删除，不能只隐藏控件。
- 删除 `gravity_G`、`GravityConfig.G_const` 及可写覆盖路径，运行直接引用共享 CGS G。
  老键报 `RETIRED_PARAMETER`，不能落入 custom。checkpoint／日志可保存只读常数身份。
- 历史 `gravity_G=1e-20` 径向验证由维护者批准等效 CGS 输入后迁移；
  不直接删键后沿用旧物理预算，不通过改 floor 或关引力恢复测试。
- `pi` 和 `exp(number)` 保持同一范围：G 删除后仅六个网格边界和三个外部加速度字段。
  本工作不扩展为通用数学表达式解析器，也不添加 e／E 常数或新语法职责。
- 参数用途在 Core 登记 `simulation | verification`，case 参数用 `(caseId,key)` 定位；
  算法精度控制不能因出现在测试中就标为测试专用。GUI 正常表单区分用途并保留显式输入的可见性。
- 参数仍按 Grid／Runtime／EOS／Network／Diffusion／Gravity 归属。
  Core 和文本输入没有 `AdvancedConfig`／advanced 标签；GUI 若分组折叠，仅为展示策略，
  缺项或错误字段必须可直接定位和展开，不因“高级”而阻断用户补齐。

### 3.3 正式接口升级

当前外层 `schemaVersion="1.0"`，配置扩展 `version="2"`。
配置缺项允许 null、来源状态扩展是破坏性变化：**配置扩展升级为 3**。
外层封套语义不变时保留 1.0；若其他命令的字段发生破坏性变化，分别升级所属扩展，
包括会话内嵌响应的版本传播，不能只改根节点字符串。

先提交 API 规范、完整候选响应和 Core／Host 共用 fixture，再接 UI。
下表冻结语义；新增字段名、JSON 结构在这一提交中确定，避免各端各猜一版。

| 对象 | 版本 3 必须表达的语义 |
| --- | --- |
| schema | required 条件、适用条件、允许默认及其来源、模板推荐、单位、用途；推荐与运行默认分别表示 |
| 参数值 | `parsedValue` 可为 null；原 token 留在 `rawValue`；invalid 不伪装成缺项或 0 |
| 来源 | input、case-defined、derived、documented-default；missing／invalid 没有虚假的有效来源 |
| 条件状态 | 已满足／不适用／上游信息不足分别可辨；缺少开关不映射为“不适用” |
| 完整性 | 部分输入仍可显示；已知缺项／错误时不通过；未执行的 Setup／文件／设备检查不能声称完成 |
| diagnostics | code、severity、parameterKey、模块、条件、期望类型／单位及位置；全局问题允许 key=null |
| identity | 原始输入字节、case、request；Host 另关联项目、源码、binary/build、会话和编辑版本 |
| execution | 检查到哪一层、哪些未执行；inspection 成功不设置 simulationReady=true |

沿用现有 stdout JSON、stderr 日志和 CLI 错误分类。
聚合增加诊断仍须受请求／响应预算约束；若超限，返回明确受限状态，不能截断为成功。
标准及自定义参数的 raw 数值、非法文本、单位未知和条件未定均须通过 Host 类型校验，
不允许在 TypeScript 中 `null ?? 0`、`Boolean(null)` 或注入默认值消除错误。

Core、Host 的运行时响应校验器和 TypeScript 类型同批升级。
不支持的版本返回可理解的“不兼容，请更新”，保留编辑文本；
不以兼容层重建旧缺项回填。刷新 `src/api/examples` 中活动输入与真实响应，
明确历史快照用途；旧 `fallback.json` 测试迁移到明确失败契约。
更新配置说明、公开 C++ 用法、有效 .par、新手示例及中英文 Reference，
不能先发布客户端而要求用户手动猜测新输入。

## 4. Studio 与 Host 工作流

### 4.1 参数工作台与身份

- 首屏从当前 binary 拉取目录／模型能力。缺项显示“待填写”；推荐值只在用户明确采用模板或编辑后写入。
  原始错误输入保持可见；诊断定位字段及文本行。检查、预览不会自动保存。
- 区块标题与字段同行展开，支持折叠，提供简短用途说明；Runtime 优先展示
  backend、积分器、求解器、重构、CFL、终止与输出。三个轴的网格控件保持同级。
- Gravity 展示 none／external／self 各自需求；G 不可编辑。
  外部加速度分量按 Core 要求展示，不能凭几何维数隐藏仍必需的零分量。
  Diffusion 主开关、通道、材料系数来源和禁止键按 Core 判定；显式移除支持 Undo。
- 枚举的单位显示“不适用”；无量纲、坐标相关、混合状态和未知单位分开显示。
  轴名来自 Core，不能提前把二维 cylindrical 改为尚未实现的 RZ。
- 配置保存与运行资格分开：允许用户明确保存未完成草稿并保留错误状态；
  Run／Restart 不因 Save 成功而开放。保存不规范化未知文本，不插入未确认的推荐值。
  覆盖确认、另存为和重新打开沿既有文件所有权规则执行。
- `configRevision` 不只比较解析后的值：空白／原文编辑也有输入身份。
  切换 case、项目、binary、构建或会话后淘汰旧响应；不能让上一模型的晚到结果覆盖当前表单。
  文件被外部修改时显示冲突，保存前核对，不能用旧缓冲区静默覆盖。
- 显示记录区分真实 Core、示例及不可用状态，不以 Mock 替代失败结果。

### 4.2 Linux／WSL、构建与独立运行

**本轮只交付 Linux／WSL2，明确不开展任何原生 Windows 适配。**
不开发、修复或优先安排 Windows launcher、exe／bat／PowerShell 包装、
安装包／签名／自动更新、原生 Windows Core／MSVC 构建、Windows 专属文件对话框、
盘符／UNC 适配、跨平台发布矩阵或 Windows CI。
已有 Windows 记录只作为历史资料，不能把它们的完成状态替代 Linux／WSL 验收。
遇到 Windows 专属问题登记为本轮范围外，后续由维护者另行决定，不能因此阻塞当前主线。

提供 `arch-studio` 本地入口及 Linux／WSL 独立窗口。
WSL 在 Windows 主机上运行只是一种宿主环境；允许使用既有 WSLg／Linux 图形环境，
但启动与进程控制留在 Linux／WSL，不通过 Windows exe／cmd／PowerShell 转发。
驱动／WSL 配额等宿主信息仅用于记录平台条件，不构成原生 Windows 适配任务。
先用 Linux 路径和目标环境的文件选择器完成实际操作验证；
浏览器自动化对 UNC 失败时不能借机改做 Windows 桌面版本。

前台配置窗口可依赖本地 Host，正式计算不依赖预览子进程的寿命。
普通 headless Core 构建不强制依赖 Node／Electron，GUI 包装不自动触发 CUDA 编译。

底部保留 Configure、Build、Update Preview、Run、Restart 和终端区域。
Configure 必须执行受控 CMake 配置，不只改前端字段；
Build 使用 CMake 构建入口，已有 Make／Ninja generator 不再对应重复按钮。
显示选定工具链、构建类型、CPU／CUDA 和实际输出程序；预览常规路径用 CPU。

Host 用明确 argv、项目目录和受控环境启动已登记操作，保持现有进程请求边界，
不为 GUI 新增任意 shell／可执行文件调用 API。路径带空格、中文、文件缺失、
构建失败、取消及重新打开均有实际检查。CMake 文件 API／构建依赖记录可用于身份追踪，
不能继续把少数硬编码输入文件列表当作完整依赖证据。

构建新鲜度至少区分 current／stale／unknown：
`dependenciesComplete=false` 时即使 `ninja: no work` 也不能标 current。
关联编译输入、工具链、配置和 binary；重新构建后更新身份。
对明确的历史 binary 可提供独立的“按已编译版本运行”流程并记录确认，
但不能声称它包含当前源码。未验证的 binary 不能冒用当前编辑源码的运行就绪状态。

Run／Restart 使用用户确认保存的精确输入和已选择的可执行文件；
运行前再次检查配置、实际资源及配对身份。Run 前端预检通过仍以 Core 启动检查为准。
Restart 选择真实 checkpoint，执行身份／布局检查与继续演化，不能仅再次运行原 .par。
重启与输入的覆盖／优先级沿 Core 契约，不由 GUI 另定义一套。

每次计算有独立、可见的前台终端及可追踪进程身份。预览取消、切换项目、关闭 Studio
或 Host 退出不能误杀已交付给终端的计算，也不能因 stdout 管道关闭中断计算。
显式 Stop 只终止其拥有的运行进程组；记录 PID、启动身份和退出码，避免按名称批量 kill。
用小型有效算例验证这些生命周期，不用大型科学轨迹测试界面按钮。

### 4.3 全模型预览与 plt：分开验收

配置／Run 完成后再扩大科学数据展示。以实际注册表列出全部当前模型，

缩放、对数、裁剪与颜色只改变显示，原始数据及无效值保持可追溯。

writer 扩展复用现有共享 IO 层，允许增加来源和网格元数据、发布及错误传播机制，

首批候选需明确文件版本与完成发布、
case／原始 config／build／binary／EOS 身份、字段单位与位置／分量基底，以及
原生活动单元的 bounds、排列和积分测度。可复用的身份与度量沿 Core 现有来源获取；
未知或未记录的项明确表示，不能从文件名、数值大小或当前选中的项目推定。
当前 `Grid/x,y,z` 是转换后的笛卡尔单元中心，原生 bounds 另行记录；单元测度复用
`GridMetrics::CellVolume`，低维每单位长度／立体角约定交维护者核定。
Reader 只消费已经发布的结果，不用“文件存在”判定写入完成；读取不加载模拟 EOS、
启动 Driver 或初始化 CUDA。修改共享 writer 的负责人唯一，避免两边各写一套格式。

维护者已准备[候选扩展验证入口](PlotfileValidationContract.zh-CN.md)，含小型反例、

仍由合作者实施；现有布局可以提交映射后适配，测试副本不规定最终存储方案。
[本轮记录](../../validation/backend/results/plotfile-contract/README.md)仅证明所列读取检查，

  长时轨迹、硬件计时和完整组合扫描保持手动入口。
- 必需验证只依赖 ARCH、所选后端和常规依赖；FLASH 不属于下载、配置、CTest、CI 或发布前置条件。
  ARCH 自己的解析解、守恒和独立参考继续保留。
- 被新契约取代的旧测试／回填设施可以退役；保留独有失败与科学覆盖，
  不能靠改数值预算、删除失败组合、空套件或 skip 取得通过。

## 7. RTX 4070 Ti：新平台的执行协议

### 7.1 平台与构建准备

RTX 4070 Ti 属于 compute capability **8.9**，RTX 3060 Ti 为 **8.6**。
新机记录 `CMAKE_CUDA_ARCHITECTURES=89`，使用满足 ARCH 构建要求、
能够原生编译 SM_89 且已验证的 CUDA 工具链；显卡型号和 capability 以实际查询为准。
不复制旧机 SM_86 缓存，也不沿用此前误记的 SM_120／CUDA 12.8 必需条件。
依据：[NVIDIA GPU 表](https://developer.nvidia.com/cuda/gpus)。

记录 GPU 型号／显存、CPU／物理核／SMT、RAM、OS／WSL 内核、驱动、Toolkit、
Host 编译器、CMake、构建选项、cuDSS／KLU 与 EOS／网络数据身份。
驱动须实际支持该 GPU 和工具链；WSL 记录 Windows 驱动，不仅记录 Linux 库版本。
cuDSS 的路径由本机安装决定，显式配置 `CUDSS_ROOT` 并检查链接／运行；
不复制另一机器的绝对路径。[cuDSS 安装要求](https://docs.nvidia.com/cuda/cudss/getting_started.html)
只说明依赖条件，最终仍以实际求解路径检查为准。

先完成 CPU 验收，再统一编译受影响 CUDA 目标；计时使用冻结 Release 构建。
共用数学、FP64 与已发布严格浮点要求保持；不得为新卡改用 float、fast-math、
较松 ODE／Poisson 精度、更少 burn 半步或更简化 EOS。
小型 cuDSS 科学残差／失败检查与大耦合模拟分开；没有实际使用稀疏路径的算例
不能算作 cuDSS 验收，也不要求每个算例强制换为稀疏解法。

### 7.2 冻结输入和已有执行入口

正式平台包由维护者确认：case、完整有效 .par、EOS／网络数据、
物理终点、分辨率、CFL、AMR／regrid、求解容差、输出频率、独立参考及预算。
合作者负责让包可重复执行，不能自行推测科学参考或替换输入。
G 退役涉及的缩放样本在批准迁移前只运行已确认不受影响的工程检查。

| 目的 | 复用的现有入口／样本 | 平台上需要的证据 |
| --- | --- | --- |
| 均匀网格与模块锚点 | [backend manifest](../../validation/backend/cases.json) 与 [通用 runner](../../tools/validate_backend_results.py) | Hydro／外部力／扩散解析检查、burn 守恒／后端检查；选择完整科学分组，不拆掉收敛对 |
| 自引力 | [现有场验证](../../validation/gravity/run_self_gravity.py)、[CUDA 接口检查](../../validation/gravity/check_cuda_compatibility.py) | 泊松残差、独立势／力参考、失败路径；不能只检查输出有 GPOT |
| 四模块／AMR | [SNIaCoupled 输入](../../simulation/SNIaCoupled/README.md)、[曲线／后端 runner](../../validation/gravity/curved/run_cuda_matrix.py) | 2D／3D Cartesian AMR 各一项，受影响曲线几何代表项；真实混合层级与模块工作量 |
| 耦合后处理／续算 | [耦合检查](../../validation/gravity/curved/verify_coupled.py)、[后端比较](../../validation/gravity/curved/compare_backends.py)、[跨后端重启](../../validation/gravity/curved/check_cross_backend_restart.py) | 物理量预算、CPU↔CUDA 续算及身份一致 |
| 设备安全 | [现有 AMR 验证入口](../../tools/validate_cuda_amr_restart.py) 与已有 sanitizer 封装 | 所改资源路径的越界／生命周期检查；与正式计时分开 |

SNIaCoupled 是厘米尺度的四模块热点执行示例，不能据此宣称完成完整 SN Ia 科学验证。
其 Setup 要求四模块一起开启，不能随意关一个开关做消融；单模块检查使用原所属入口。
Helmholtz 当前恒星扩散路径为热传导，不能将打开所有开关写成三种输运都已参与。
纯流体或小型单区模型的 GPU 负收益照实记录，不要求每个模型都加速。

**现有 runner 还不是即取即用的整程计时包。**
`run_cuda_matrix.py` 的 `--pair` 接受步数，`check_cuda_compatibility.py`
的 benchmark 也有步数上限；它们可保留作短检查。
实施时在现有执行／取证工具中补齐“指定物理终点”模式，复用后处理与证据结构，
确认 max_steps 没有提前截停。终点比较不得要求 CPU／GPU 恰好同一步数；
自适应轨迹的合理差别由共同误差预算判断，不靠强行对齐步数掩盖。
维护者冻结终点与预算后，提交可复制的一条执行命令和完整 manifest，
再开始新机正式计时。无需另建一个仅支持 4070 Ti 的验证器。

### 7.3 计时定义与重复策略

1. 每个对比完成同一物理终点 `t_end`，相同问题、精度、CFL、网格／AMR 和输出；
   墙钟耗时 `T` 与物理时间分别记列，不把单步耗时作为主加速比。
2. 主对比在同一 CUDA Release binary 中显式选择 CPU／CUDA，排除构建差异；
   同时保留 CPU-only Release 的生产基线。报告两种 CPU 基线，不能只选较慢者。
   记录 resolved backend，GPU 结果不能由自动 CPU 路径产生。
3. CPU 线程／亲和性先做有限候选筛选，再冻结正式线程数；记录线程清单和全部筛选结果。
   至少保留 CPU1 诊断与本机最佳实测 CPU。跨主机比较另给相同线程数结果；
   不用旧机 16 线程套用新机，也不以 SMT 数量冒充物理核。
   CUDA 路径中的 Host AMR 等 CPU 工作也记录线程与亲和性；按同一主机资源预算预先冻结，
   不能隐藏其 CPU 成本，或把旧脚本强制单线程当成新平台最优设置。
4. 各后端先一次独立预热，再至少三次成对交替运行，交替首跑后端，
   每次使用新输出目录。完整记录每次值，给中位数、最小／最大和样本数。
   首次加载成本单列；不能只保留最快一次。
5. 主指标为进程启动至成功退出并完成输出的单调墙钟时间，包含初始化、EOS 加载和 I/O；
   Driver 耗时与模块计数作为归因辅助，重叠区间不相加。
   编译、sanitizer、profiling、GUI 启动另计，不能混入或只为 GPU 扣除。
6. 正式计时关闭其他 GPU 重负载、预览渲染与编译，记录功耗／温度／利用率、
   CPU 频率策略、主机内存和显存峰值及采样工具。
   WSL 不能取得某指标时标 unavailable，不填 0。
   波动明显时保留原批次、说明干扰，再整批复测，不按快慢选择性剔除。
7. 本机加速比 `S = median(T_CPU) / median(T_CUDA)`，并排显示绝对秒数和误差指标。
   跨 3060 Ti／4070 Ti 的不同主机结果标为“平台比较”，CPU、驱动、工具链和 I/O
   差异都可能影响结果；不能直接把平台倍数解释为显卡或 FP64 吞吐提升。
   H100 后续使用同一协议，消费级新卡不能替代其验证。
8. 代表耦合场景正向加速仍为目标；未达到时交付完整失败／负收益记录，
   由维护者判断工程瓶颈或当前能力边界。此时不能写“性能验收通过”，
   也不能通过减少物理工作制造正向收益。契约通过、科学通过、性能测量分别定状态。

本阶段扩展到 O7.1–O7.5 及部分 O9。14700K 的混合核心筛选、可见拓扑／WSL 限制，
和 30–60 分钟量级长轨迹的冻结／采样／续算规则见[执行细则第 5 节](JeansRZPlatformHandoff.zh-CN.md#5-部分-o9第二平台数据集)。
先完成对应数学／接口短验证和独立预算，再做已具备内置边界的长时子集。
依赖 O8 或未明确收支的任务保持待前置；新卡工程通过不等于整个 O9 已完成。

## 8. 合作者须识别的信号与交回我们的内容

| 现象 | 合作者可以处理 | 必须记录并交 ARCH 维护者判断 |
| --- | --- | --- |
| 配置缺项、schema／Host 类型不匹配、旧响应覆盖 | 按已冻结契约修复及回归 | 契约有歧义的键／条件／来源及最小输入，不能自行给物理默认 |
| 编译、文件路径、设备分配、同步／资源生命周期问题 | 在既有数学不变前提下定位和修复 | 修改所有权、前后证据；新 toolkit 导致的数值差异 |
| NaN／Inf、非正密度、不可解析热能、EOS 越界、ODE 失败 | 保存首个错误和可复现输入，停止该轨迹验收 | 状态、时刻、单元／层级、有效参数、日志和输入身份 |
| 正值修复、守恒偏移、Poisson 残差超限、后端差异超预算 | 执行原检查并记录实际值及阈值 | 守恒含源项／边界收支，不能凭“能量应恒定”另定判据；不改容差／floor |
| GPU 比 CPU 慢、3D 成本增长、AMR 工作量不同 | 独立采样模块时间、调用／传输／同步与 cell 更新数 | 原始时间、工作量、数值指标；不同步阶不直接判为实现错误 |
| 坐标场／plt 看起来异常 | 核对轴、单位、原生单元、读取与显示链路 | 物理合理性、参考解及几何权重由维护者判定 |
| 舍入边界或测试参考疑似不适用 | 记录 ULP／绝对／相对误差和参考来源 | 提出调整依据；未经科学评审不放宽门槛，也不以删除测试解决 |

维护者提供独立参考、误差预算及应存在的物理贡献，合作者负责执行并收集。
CPU/GPU 数值一致只能证明二者一致，不能单独证明物理正确；
既有解析／独立参考与守恒检查必须继续保留。对方不需要给出天体物理解释。

### 9.1 先本机处理，再交付结果

**本阶段不得上传新运行产生的 H5/HDF5、plt、checkpoint、完整场数组、
Nsight 原始 trace 或其他大型二进制 raw data。**
该要求覆盖 Git 提交／push、Git LFS、PR 附件、CI artifacts 和其他远端存储；
压缩、改后缀、分片或转为完整 JSON/CSV 数组都不能替代数据处理。
仓库既有、经管理的数据资产不是本轮新运行输出，不能借清理提交将其删除。

交付前在本机完成：

1. 核对 source／binary／输入身份、退出码、实际物理终点及输出完整性；
   数据缺失、读取失败、轨迹提前终止明确记录，不能让空结果通过。
2. 用现有分析器读取原始文件，按真实单元体积／面积生成冻结预算需要的
   误差、残差、守恒／边界收支、极值、修复、模块贡献和续算指标。
   不改写原始值，不用裁剪或稀疏采样掩盖异常。
3. 导出精简的汇总 JSON/CSV、逐次计时表、必要的降采样趋势图／对照图、
   指定异常的诊断片段和运行元数据。数值范数／最坏误差从完整数据计算，
   图像降采样只服务显示；处理脚本、字段／单位和输入身份一并可复现。
4. 人工核对文件清单、格式和大小，自动化打包采用明确允许的文件集合，
   不打包整个输出目录。保留现有 CI 指定诊断路径，不扩大为整个构建／输出目录上传；
   CTest/JUnit 和必要短日志可沿已有入口提交。允许结果含 failed／pending，失败摘要同样保留。
5. 检查待提交文件和实际上传清单；未被引用的中间文件、无关全量日志／trace、
   含本机隐私路径或环境秘密的内容留在本地，提交必要且已检查的诊断摘要。

原始数据保存在对方机器的持久目录，登记本地数据编号、相对文件名、尺寸、
关联身份与保留安排；报告可以引用这些编号供维护者提出具体复核请求。
原始数据仍在本地不妨碍提交处理后的报告。需要查看特定原始片段时，
先确定最小范围和交付方式，另行确认后处理，不能默认整包上传。

### 9.2 完成判定

阶段状态分别登记“实现完成”“工程验证通过”“科学评审通过”“性能结果”。

- [ ] 没有把 Windows 原生适配、打包或旧 Windows launcher 的问题放进本轮前置与交付范围。
- [ ] 受影响 CPU／CUDA 检查齐全，科学异常已有结论或明确保持未通过。
- [ ] 同物理终点的平台计时、正负收益和全部原始值可复核，未用短步数替代。
