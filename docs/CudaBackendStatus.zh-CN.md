# CUDA 后端与 GPU-AMR 能力

英文原文：[CudaBackendStatus.md](CudaBackendStatus.md)。英文版是规范文本。

*后端*（backend）是指 ARCH 中负责在特定硬件上执行计算的引擎。CUDA 是我们的 GPU 后端：选择它会改变底层的执行与内存管理方式，但它严格保留了与 CPU 完全相同的物理模型和逻辑。*自适应网格细化*（AMR）会在模拟过程中动态调整单元尺寸，确保复杂的区域能获得更高的空间分辨率。本指南将详细说明这两种处理器之间的分工，并帮助你选择一个兼容的配置。

CUDA 后端会在 GPU 上执行流体动力学与自适应网格的数值计算。CPU 和 CUDA 路径共用同一套数学与物理实现；而设备内存、计算核（kernels）、执行流以及线性求解库则是后端专有的。两个后端均支持下述功能范围。受测配置、技术结果和整体验收状态统一记录在[验证索引](../validation/README.zh-CN.md)中。

## 共用功能范围

| 模块 | 已有实现范围 |
|---|---|
| 流体 | Van Leer、Steger-Warming、Roe、HLL、HLLC；PCM/MUSCL/PPM；MinMod/MC/SuperBee/Van Leer 限制器；Euler/SSPRK2/SSPRK3 |
| 网格与几何 | 一、二、三维块网格；笛卡尔、柱坐标与球坐标，采用两端共用的坐标约定 |
| 边界 | 周期、流出、反射 |
| 动态 AMR | 细化指标、守恒插值与限制、跨层交换、流体／扩散通量修正和事务式状态迁移 |
| EOS | 理想气体、Helmholtz、规范化 Tabular3D/Tabular4D 数据布局 |
| 扩散 | 组分、热、黏性模式及 RKL1/RKL2 |
| 重力 | 使用共用分阶段源项的外部重力 |
| 内置燃烧 | iso7、aprox13、aprox19、aprox21；BE_NR、BD、ROS4 和网络受限 NSE |
| 生成网络燃烧 | 已注册且数学实现可在设备端运行的网络；支持已识别的内嵌弱反应率表，各后端分别保存只读数据；按下述规则执行稠密或稀疏求解 |
| 输出与恢复 | 共用 HDF5/checkpoint 设施，在 IO 边界同步状态，并提供 CPU/CUDA 重启路径 |

策略名称、别名和支持的组合来自同一注册系统。状态方程（EOS）联系压力、密度、
能量和组分，反应网络描述组分如何变化。它们采用编译期鸭子类型（duck typing）
接口：模型提供约定的操作，编译器将这些操作接到调用者。后端适配层只连接存储
或求解器，不另建物理模型。核统计平衡（NSE）在所选支持网络的核素集合内求出
平衡组分；网络可以是内置网络或明确认证的生成模型。具体配置见
[API 与参数参考](Reference.zh-CN.md)。

二维柱坐标与球坐标网格都采用极坐标平面 `(r, phi)`，其中 `phi` 是以弧度表示的
方位角；三维球坐标使用 `(r, theta, phi)`。

## GPU-AMR 执行方式

实现入口见 [CUDA runtime](../src/cuda/runtime/README.md)和[共用 AMR 模块](../src/amr/README.md)。

CPU 掌握网格拓扑、Morton 排序以及所有的细化/粗化决策。

- **拓扑**描述了网格块之间的连接关系。
- **Morton 排序**为这些网格块分配了一个空间上连续的索引。
- **细化**会将单元分裂得更小以提高分辨率，而当配置的指标允许时，**粗化**则会将它们重新合并。

相反，GPU 负责计算具体的单元指标，并只向主机回传每个网格块的一个汇总值，以辅助这些网格决策。场数据的守恒迁移直接在设备缓冲区上进行，它精确复用了 CPU 路径的传输数学公式。这种设计确保了宏观的网格决策仍由 CPU 控制，而繁重的体量级场计算则留在 GPU 上处理。在写出检查点或绘图数据时，只有必需的字段会被显式复制回共用的主机写入器。

## 按性能选择后端

**在已测的多物理 AMR 算例中，GPU 的端到端加速最高约为 5 倍。**
最高结果来自 128 个初始网格块的流体、BD 燃烧、RKL2 全输运和动态 AMR 耦合算例：
CPU16 耗时 423.55 秒，CUDA 耗时 83.35 秒，加速比为 5.08 倍。这里比较的是同一物理
问题在两种后端上从启动到结束的完整运行时间。

测量使用 H100-20C **20 GiB vGPU** 和 Xeon Gold 6338 **32 vCPU 虚拟机**，
并非独占的完整 H100 或 32 个独占物理 CPU 核。燃烧与耦合算例使用 aprox13、Helmholtz EOS
和 DenseLU，纯扩散算例使用理想气体 EOS。CPU 基准取 1、8、16 线程中耗时中位数最短的配置。每种配置先预热一次，
再交替进行 CPU/CUDA 正式采样，每种配置取五次正式运行的中位数。

下表的定义为 `加速比 = CPU 耗时 / CUDA 耗时`：大于 1 表示 CUDA 更快，
小于 1 表示 CPU 更快。块数是 **AMR 初始网格块数**，不是 CUDA 线程块数，
也不是细化后的单元总数。“耦合”包含流体、燃烧、组分／热／黏性扩散及动态 AMR。

| 算例 | 8 块 | 32 块 | 128 块 |
| --- | ---: | ---: | ---: |
| 扩散，RKL1 | 0.099× | 0.392× | 1.004× |
| 扩散，RKL2 | 0.116× | 0.489× | 1.347× |
| 燃烧，BE_NR | 0.964× | 1.325× | 1.978× |
| 燃烧，BD | 1.046× | 1.519× | 2.612× |
| 燃烧，ROS4 | 0.975× | 1.300× | 1.997× |
| 耦合，BE_NR + RKL1 | 1.183× | 1.460× | 2.876× |
| 耦合，BE_NR + RKL2 | 1.293× | 1.962× | 3.999× |
| 耦合，BD + RKL1 | 1.378× | 3.179× | 3.924× |
| 耦合，BD + RKL2 | 1.460× | 2.856× | **5.082×** |
| 耦合，ROS4 + RKL1 | 1.248× | 2.245× | 3.681× |
| 耦合，ROS4 + RKL2 | 1.363× | 2.868× | **5.007×** |

另一组开启动态 AMR 的二维 Sedov 测试，在 4×4、8×8 初始网格块布局下分别测得
1.588 倍、1.667 倍加速。这是流体与 AMR 一起运行的结果，不能解释为 AMR 单独的加速比。
绝对耗时、验收数量及固定版本的原始报告见
[验证汇总](../validation/backend/results/hpc-cuda-optimization/README.md)。

更多网格计算有助于摊薄 CUDA 启动计算核和同步的开销。小规模扩散算例仍由 CPU 占优，
128 块的 RKL1 也基本只是持平。增加核素数量是另一种规模变化，并不会自动提高 GPU 利用率。

**大网络性能提醒：已测的生产路线 150/200 核素稀疏应用仍存在负加速，CUDA 耗时约为
CPU8 的 5.0–10.3 倍**，对应加速比约为 0.10–0.20。其数值对照已经通过，但当前由主机
协调的 cuDSS 执行路径在这些小规模完整程序算例中仍有性能限制。此类工作负载建议优先
使用 CPU，除非自己的代表性算例已测得 GPU 收益。更大的网格与网络组合需要单独测量，
不能套用上面的 5 倍结论；实验性稀疏求解器目前不作为生产选项。

选择后端时，用自己的代表性输入比较整段运行时间即可。
`compute_backend = auto` 选择可用且支持当前配置的后端，不会替用户测速。
端到端时间包括初始化和输出；重网格耗时已包含在其中，不能重复相加。

测速时，两端应使用相同的物理输入、AMR 判据和输出设置。

### CUDA 优化具体改变了什么

- 流体、扩散和小网络燃烧在工作区布局允许时，一次启动处理多个网格块；内部仍调用
  共用的单元／面数学运算和已注册物理策略。
- AMR 场数据在设备上迁移，只把紧凑的指标摘要交给 CPU，供共用网格树逻辑进行决策。
- 设备工作区和主机交换缓冲区复用已有容量。网格拓扑变化后重建受影响的数据视图，
  不另写物理模型，也不继续使用失效的网格引用。
- 执行完成状态和场版本检查协调边界更新、交换及结果发布。复用已经完成的边界数据，
  避免主机读取已接受状态前发生多余刷新。
- 稀疏修正量统一采用针对原始方程组的残差检查。cuDSS 分解存储及有上限的缓存属于
  后端实现；大网络的进一步加速作为后续独立优化任务。

这些调整共同减少计算核启动、分配和传输开销，不改变物理方程或验收容差。
加速比描述的是完整算例，不能把整体收益单独归于其中某一项改动。

## 稠密与稀疏燃烧求解

核燃烧通过一组常微分方程（ODE）推进。方程数为核素数加温度方程；需要积分
有符号弱反应损失的网络另含一个能量源状态。
`linear_solver = Auto` 下，总数不超过 31 个方程使用共用 DenseLU
（不含辅助状态时最多 30 核素，含该状态时最多 29 核素）；更大系统选择 CPU KLU 或 GPU cuDSS。
相应求解库及网络／EOS 执行代码必须已构建。显式指定 CPU+cuDSS 或 CUDA+KLU
会被拒绝；显式 CUDA 不会静默回退到 CPU 物理计算。
`compute_backend = auto` 可在启动时选择可用且支持该配置的后端并报告选择，
进入构造后不再切换。

稠密求解存储完整的小矩阵，稀疏求解主要存储非零项；CSR（压缩稀疏行）按行组织
这些非零项。CUDA 稀疏执行器让数值状态和 CSR 矩阵保留在 GPU，主机调用 cuDSS API 并交换
执行请求和响应。矩阵分解的存储设有上限，内存需求取决于分解产生的非零项和实际工作负载。
当前适配层使用 cuDSS 0.8 API 和非对称 BTF/COLAMD 排序，并对原始矩阵
检查修正量残差。原生执行/资源错误会明确报告，不伪装成 ODE 重试。

ARCH 支持 pynucastro 生成的反应网络，并通过 CPU KLU / GPU cuDSS 提供稀疏求解。
对于超大网络，具体模型的科学可靠性取决于核素集合、反应数据和适用范围；
资源需求随网络与网格规模增长。

## 网络和表格数据的选择

- 生成的弱反应率表在两侧共用插值、导数和能量积分。生成器会检查表格布局并
  报告不支持的输入。CUDA 需要具备设备端数学实现并满足包接口要求的生成网络，
  配置时会根据清单检查这些能力。仅提供 CPU 接口的包在 CPU 上执行；准确的
  清单字段见[网络契约](Reference.zh-CN.md)。
  独立 Urca 轨迹结果见[网络验证](../validation/network/README.zh-CN.md)。
- 自引力仍不是两端现有生产功能。通过核数据与平衡模型检查的生成网络可使用
  共用的 NSE 数学实现，并完成定点 CPU／CUDA 检查；这不等于新增完整应用级资格验收。详见
  [模型边界](../src/physics/nse/README.md)。内置与生成 NSE 都受所选核素集合限制，
  alpha-chain 网络不能替代通用 NSE 网络。
- ARCH 规范化 EOS 表不能直接替换为任意原生核物质表；单位、热力学分量与能量
  零点必须满足[表格契约](../src/physics/eos/TabularEOS.zh-CN.md)。
  原生 EOSDriver 与受支持的重子 ASCII 源格式复用现有表所有者。分量在主机
  加载时补齐，严格插值、导数及全根温度反演共用同一 CPU/CUDA 数学实现；
  其聚焦扩展检查与历史完整 CUDA 发布验收分开记录。
- 本地发布验证使用有代表性的生成网络和弱反应网络。更大模型的轨迹和资源
  测量安排在适合其规模的机器上。ARCH 当前采用单机 CPU 或单 GPU CUDA 执行。

[验证索引](../validation/README.zh-CN.md)区分数值结果与实现声明，并提供可复现的
输入和指标。贡献者实验日志和机型相关证据单独保留在
[开发记录](development/README.md)，不混入本功能指南。
