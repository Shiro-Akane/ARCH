# ARCH v1.1.0

Chinese translation: [V1.1.0.zh-CN.md](V1.1.0.zh-CN.md).

This release focuses on faster CUDA execution with dynamic adaptive mesh
refinement (AMR), while keeping a single mathematical and physical implementation
for CPU and GPU. It also makes the source tree, documentation and validation
entry points easier to navigate. It is a source release: build ARCH locally and
retrieve the required runtime tables with `git lfs pull`.

## Highlights

- **Batched CUDA execution.** Hydro, diffusion and small-network burning process
  multiple mesh blocks per kernel launch where their storage layout permits.
  Device workspaces and host exchange buffers reuse capacity between steps.
- **Device-resident AMR data handling.** CUDA evaluates refinement indicators
  and performs conservative field migration. The CPU retains the common mesh
  tree, Morton ordering and refinement/coarsening decisions; there is no second
  GPU-specific refinement algorithm.
- **Consistent coupled evolution.** Burning, diffusion and Hydro retain the
  shared stage order and physical policies. Burn energy, composition closure
  and sparse residual acceptance use their common mathematical implementations.
  Completion and field-version checks keep exchanged and restored state coherent.
- **Clearer verification and documentation.** User guides explain configuration
  and measured performance; module-level validation summaries explain methods
  and errors before linking detailed evidence. Reusable tests and tools remain
  included for users who want to check their own build.

## Measured performance

The accepted benchmark campaign used an **H100-20C 20 GiB vGPU** and a Xeon
Gold 6338 virtual machine exposing 32 vCPUs. Microphysics timings are medians of
five formal runs after a warm-up. The CPU reference is the fastest measured
configuration among 1, 8 and 16 threads. Times include initialization and output,
not just GPU kernels.

| Workload | Measured CPU/CUDA speedup |
| --- | ---: |
| Hydro, aprox13 burning, full transport and dynamic AMR; 128 initial blocks | 2.88–5.08× across six ODE/transport combinations |
| aprox13 burning; 128 initial blocks | 1.98–2.61× across three ODE methods |
| Diffusion; 128 initial blocks | RKL1 approximately equal; RKL2 1.35× |
| 2D Sedov with dynamic AMR; two mesh sizes | 1.59–1.67× |

The highest result uses BD burning with RKL2 transport and the Helmholtz EOS:
**423.55 seconds on CPU16 versus 83.35 seconds on CUDA, or 5.08× speedup**.
Speedup means CPU execution time divided by CUDA execution time for the same
case. Small problems may still favor CPU.
See the [performance report](../../validation/backend/results/hpc-cuda-optimization/README.md)
for the input definitions, scaling and measurement protocol.

**Large reaction networks need separate performance consideration.** Numerical
comparisons passed for the tested production 150/200-isotope configurations,
but their small full-application workloads took about 5.0–10.3 times longer on
CUDA than on CPU8. Use CPU for comparable workloads unless a representative
measurement shows a GPU benefit. Further sparse-solver acceleration remains
planned; the approximately 5× aprox13 result does not describe these networks.

## Verification

The source-identified optimization campaign contains **1,188 microphysics runs
and 1,155 passing comparisons**, with separate Hydro/AMR and large-network
checks. Integration checks cover shared AMR contracts, active burn-energy
timestep limiting, coupled transport, checkpoint continuation and focused
CUDA memory/race instrumentation. The
[Validation index](../../validation/README.md) distinguishes numerical accuracy,
backend agreement and performance evidence, including which source and binary
each check exercised. The full benchmark campaign is not repeated or relabeled
by the release-preparation cleanup.

Focused release checks confirm unchanged AMR results in one, two and three
dimensions on CPU and CUDA, including continuation from pre-cleanup checkpoints.
The selected AMR tests also pass memory and race instrumentation.

## Building and using this release

Start with the [build guide](../guides/Build.md) and
[simulation case guide](../guides/SimulationCase.md). CPU-only builds do not
need a CUDA toolkit. CUDA builds support both CPU and GPU execution; enabling
CUDA or the test suite increases compilation time and host-memory demand.
Choose build concurrency to match available memory; runtime numerical settings
are not reduced to accommodate a particular development machine.

Small burning systems use the shared DenseLU implementation. With automatic
selection, sparse systems use KLU on CPU or cuDSS on CUDA; explicit unsupported
backend/provider combinations are rejected. Generated pynucastro networks
remain supported through the documented generation workflow. Their usable
scale and cost depend on the network and available resources.

The release does not include predictive-AMR/GNN data collection or inference.
Standard dynamic AMR is unaffected. Parameter files need only the AMR settings
listed in the [Reference](../Reference.md); experimental `predictive_amr_*`
settings should be removed. Internal configuration and block layouts changed,
so rebuild from the release source rather than mixing older object files or
libraries with its headers. The checkpoint format is unchanged by this cleanup.

ARCH's code license and the separate terms for scientific code and data are
listed in [THIRD_PARTY_NOTICES](../../THIRD_PARTY_NOTICES.md). Prebuilt CUDA
libraries, simulation HDF5 outputs and private experiment archives are not
release assets. Required scientific tables retain their documented Git LFS
distribution and provenance.
