# ARCH v1.4.1 — simpler builds and clearer workflows

[中文](V1.4.1.zh-CN.md) · [Release index](README.md) · [Build](../guides/Build.md) · [Studio](../guides/Studio.md)

Released **2026-11-02** · [GitHub release](https://github.com/Shiro-Akane/ARCH/releases/tag/v1.4.1)

## Build and installation

Linux and native Windows now have prepared profiles for Core, Core with CUDA, and either configuration with Studio. Dependency preparation, CMake configuration and compilation each use one command. CUDA-enabled builds retain CPU execution; `compute_backend` selects the execution backend at runtime.

- Dependency preparation selects or builds HDF5 for the chosen compiler ABI and reuses the shared HighFive and KLU configuration. Explicit dependency paths are checked against the selected installation.
- Windows CLI and Studio share the configured compiler and runtime-library environment. Generated launchers supply the required native tools and libraries.
- Studio reuses its locked npm dependencies after ordinary source edits and restores them when `node_modules` has been removed.

The [build guide](../guides/Build.md) covers prerequisites, profiles, custom tool paths, offline preparation and advanced options. Existing direct CMake configuration remains available.

## Studio and documentation

Launching `arch-studio` without arguments opens the project-selection page. CLI options can instead select an existing build, model and parameter file. Machine-specific legacy build profiles have been replaced by explicit selection of a project's build directory.

The README separates Core preparation, configuration, compilation and execution; its Studio section explains how to add the desktop to an existing Core build. Linux and Windows compilation details are collected in the Build guide. The illustrated Studio guide follows project selection, Config, parameter editing, Preview, Run and Plotfile inspection, including the working-directory rules for paths inside `.par` files.

Documentation navigation now leads to maintained usage, implementation and scientific validation material. Superseded plans, progress reports and intermediate debugging records have been removed from the distributed documentation.

## cuDSS and Run checks

cuDSS remains optional for ordinary CUDA builds. CUDA hydrodynamics and small DenseLU burning systems can run without it; the CMake capability summary states whether GPU sparse solving is available.

Core's `--check-run` query and Studio's Run preparation use the same backend-resolution logic. They report the requested and selected backend, linear solver and any fallback reason before mesh construction. Requests that require cuDSS are rejected when that provider is unavailable, whether CUDA was explicitly selected or cuDSS was pinned as the solver. Auto backend and Auto solver selection can use CPU KLU when that route supports the configuration.

Windows builds linked to cuDSS check their required DLLs in the prepared launch environment. Linux loads the vendor libraries only when the selected route needs them. `ARCH_REQUIRE_CUDSS=ON` and the `arch-check-cudss` target provide strict GPU sparse qualification; an unavailable GPU fails these checks rather than being counted as a skipped success.

## Compatibility and validation

The mathematical implementations, memory pools and scientific file readers and writers are unchanged. Linux remains recommended; native Windows supports the corresponding CPU/CUDA and Studio workflows, subject to the configurations and limitations in [Platform support](PlatformSupport.md).

Targeted validation includes the Run API contract (9 Linux and 8 Windows tests), the applicable Studio tests (464 Linux and 29 Windows), and four strict cuDSS GPU tests on each platform. Actual CUDA Sod and DenseLU runs passed. Linux checks also removed a private cuDSS library copy to verify that ordinary CUDA runs continue while requests requiring cuDSS are rejected.

Build checks cover the Linux Core/Studio profiles and linked CUDA application, plus Windows dependency preparation, project configuration, native helpers and an incremental MSVC/CUDA application build. Large-network Auto-to-KLU selection is covered by capability tests with native runtime probes; a new full large-network evolution is outside this validation set. Scientific acceptance criteria and reproducible cases remain in the [validation index](../../validation/README.md).

The dependency audit reports moderate resource-exhaustion advisories in development tools: [glob 13.0.6](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4) and [minimatch 10.2.6](https://github.com/advisories/GHSA-g3hv-75wg-m249). The 16 affected dependency entries are all marked as development dependencies in the lockfile. The suggested automated fixes change major toolchain versions; this release retains the validated dependency versions.
